## 2. Standing rules

- **A comment is not a gate. Deletion is.** A comment claiming code is safe is worse than none.
  The comment above `HEADER_CSS` asserted it "can never produce a hydration mismatch" three
  lines above the code that did.
- **CSS comments are dangerous here.** Three separate bugs: a quoted figure in a comment broke
  hydration; an apostrophe in a comment is still live on `/login`; a comment describing an
  anti-pattern triggered a false-positive lint finding.
- **One name, two jobs, and the second job surprises whoever reuses it.** `.serif` switched the
  family *and* slanted it. `--ink` is a foreground token that got used as a background.
  `.page-fade` both animates and pads, so nesting it doubled the padding. **A class or token
  does one thing, or it gets two names.**
- **A background never maps to a foreground token,** however close the hex looks.
- **Nothing invented ships.** Every figure from SEED_CARDS, the engine, or cached fares. If it
  can't be computed, drop the element, not the honesty.
- **One number, one meaning.** Two surfaces showing the same thing read from one source.
- **Measure, don't eyeball.** `tsc` can never catch CSS-token drift. And when you neutralise a
  rule to test whether it's needed, neutralise *all* of it — a half-neutralised test produced a
  confident wrong answer this week.
- **Don't tune copy to hit a pixel number.** Convergence targets are per tab group, single
  digits; anything under ~35px at 375px is fine. Copy wins.
- **Animation-gated content is a correctness bug, not polish.**
- **globals.css is the bug factory** — it has produced most of this week's findings.

## 5. Permanent knowledge — the hydration defect

**React escapes `"` → `&quot;` and `'` → `&#x27;` in the TEXT CHILD of a `<style>` tag. But
`<style>` is an HTML raw-text element, so the browser never decodes the entity.** Server DOM
has `&quot;`, client render produces `"`, they diverge at the first quote → React #425 → #423
(discards and client-renders the entire root) → #329. Because `data-theme` is set only by the
pre-paint script in `app/layout.tsx:45` and never appears in JSX, the rebuilt `<html>` loses it.

This was the disease behind the whole theme saga — stripped `data-theme`, the four-way desync,
the dark flash, the `/dashboard` hydration cascade — all of which had been patched, not fixed.

**Fix is a CSS module or imported `.css` — never `dangerouslySetInnerHTML`,** which bypasses
the escaping rather than removing the tag.

## 6. PRICING — specced, blocked on two decisions

### The settled ladder (7 Aug), durations not tiers
| Plan | Price | Daily allowance |
|---|---|---|
| Free | — | 5 searches + 5 flight searches |
| Monthly | ₹149 | 15/day |
| 6 months | ₹499 | 30/day |
| 12 months | ₹999 | 50/day, all AI features, early app access, first access to new features |

Every plan includes the CreditIQ AI WhatsApp assistant. Caps are cost control — Gogo's words:
*"someone can really spam us out for more bill."*

**Decided:** keep ₹999 and sell the annual on capability, **not** on price — because ₹499/6mo is
₹83.17/month and ₹999/12mo is ₹83.25/month, so the annual is fractionally *worse* per month and
two consecutive 6-month plans cost ₹998. No per-month figures on the 6- and 12-month cards.

**Note:** Free drops from 10 general searches to 5, which changes
`docs/PRICING-METER-DECISIONS.md` — update the doc as part of the build.

### Two decisions only Gogo can make
1. **Is this a deliberate reprice?** The live Razorpay plans are **₹199 / ₹999 / ₹1499**. The
   ladder cuts them to ₹149 / ₹499 / ₹999 — roughly half on both longer tiers. Razorpay amounts
   are immutable, so it needs three new Plan objects and three env vars repointed.
2. **Does "pay once, not a subscription" come off the site?** The backend runs Razorpay
   **subscriptions with auto-renewing mandates**. `/plans`, `PricingTeaser` and the landing all
   promise one-time. On a financial product in India the terms mismatch is the sharper half of
   the problem. Either the checkout moves to one-time orders or the copy changes.

### Also needs Gogo, two minutes
**Open the Razorpay Dashboard and read what `RAZORPAY_PLAN_MONTHLY`, `_6MO` and `_12MO` are
actually set to.** The code never sends an amount — only a `plan_id` — so the real charged
figure is unverifiable from the repo. Everything above is guesswork until this is checked.

### Current live state
- `/plans` has **no checkout at all** — its only interactive element is a "← Back" link. So
  nothing bills wrongly; the funnel is simply broken. The sole caller of
  `/api/razorpay/create-subscription` is `app/(shell)/pro/page.tsx:70`.
- Three surfaces disagree: `/plans` + PricingTeaser + landing say ₹499/₹799 "one-time";
  `/pro` says ₹999/₹1,499 "auto-renews".

### The build spec (ready when unblocked)
Four cards, "Everything in X, plus:" structure, Get Started → `/login`, light tokens from
DESIGN.md, no italic, mobile-first. **The closer should be computed, not typed** — the dashboard
already derives the signed-in user's own spread (8,76,499 pts ≈ ₹2,19,125–₹15,77,698), which is
far stronger than an illustrative ratio. Gogo's "10K → 25K" phrasing actually *understates* the
engine's own 3.6× figure.

### First-run flow (decided, not built)
Show the plan screen once after first sign-in, with **Free as a genuine one-tap continue** — no
pre-selected paid option, no disabled button. Separately wire the **paywall modal at the cap**
("You've used your N searches for today"), which is the moment that actually converts.

Needs new first-run state: paid users have a `subscriptions` row, free users have none, so
nothing records "this user chose Free". It also sits in front of the existing onboarding/Tour,
and the signed-in redirect to `/dashboard` has to route through the gate **without
reintroducing the loop fixed in `fix/shell-boundary`**.

### The meter itself is unbuilt
Nothing enforces any allowance today, including Free. The ladder's numbers can display but not
gate. Statement Truth is the exception — a binary `isPro` check, so all paid tiers pass and Free
doesn't, with zero backend change needed.
